# 製品変更前の設計確認(提案のみ・**未実装・要作者の明示承認**)
ゲーム仕様・難易度・採用素材・演出は変更しない。以下はすべて「承認されたら実装する最小案」と、その根拠となる測定。テストの assert・許容時間は緩めない。

## 1. 単発画像の先読み
**対象(最小)**: `lou_support_heal.png`、`lou_support_charge.png`、`fiona_skill_charge.png`(いずれも 1536x1024、PNG 約 3.2〜3.5 MB、デコード後 約 6.3 MB。計 約 10 MB 転送 / 約 19 MB デコード)。`fiona_skill_heal.png` は既に `motion-manifest.json` の多コマ先読み対象なので除外。
根拠: 未準備が実測で出るのは Lou heal(先読みなし 28/32)と Fiona 側の単発 charge。他の単発 still(Aidan/Fiona/Lou で計 約 120 MB)を全部先読みするのは過大で、メモリと負荷の面で推奨しない。**A/B で測ったのは 4 枚(上記 3 枚+`fiona_skill_heal`)で、3 枚だけの再測定はしていない**(3 枚は 4 枚の部分集合。承認後の実装時に再測定する)。
**方法**: データ駆動。`img/battle/motion-manifest.json` に `"preloadStills": ["lou/lou_support_heal.png", ...]` を追加し、`BattleMotion.load()` の既存 `preload()` と同じ `Image()+decoding='async'+decode()` で、既存の `cache` Map に保持する(参照を持つのでキャッシュから落ちにくい)。製品の描画経路(`<img src>` の代入)は変更しない。
**実行タイミング**: ゲーム起動時ではなく**戦闘開始時**(`BattleOpening.play()` の直後、またはパーティに該当キャラがいる場合のみ)。await せず非同期で、戦闘開始・ターン進行を一切ブロックしない。重複は `cache.has(url)` で防ぐ。
**失敗時のフォールバック**: `decode().catch(()=>{})` で握りつぶし、従来どおり使用時に遅延ロード(現状と同じ挙動に戻るだけ)。manifest に項目がなければ何もしない(ロールバックは項目を消すだけ)。
**性能(測定済み、CPU 競合2本+CPU×4 / 無負荷、PC 1280x720)**: 先読みの所要 負荷下 0.4〜3.1 秒・無負荷 0.25〜0.56 秒(非同期)。先読み中の long task は 最大 189ms(負荷下)/ 57ms(無負荷)。
**効果(同条件 A/B)**: Lou heal の mid(+250ms)未準備 28/32 → 0/32、Fiona 2/32 → 0/32、縦持ち 3/6 → 0/6、無負荷 0/8 → 0/8(`preload_ab/*.json`)。
**副作用・リスク**: 戦闘開始直後の一時的なネットワーク/デコード負荷(低性能 Android で長く・重くなる可能性。**Android 実機は NOT_RUN**)。メモリ 約 19 MB 増。負荷下では先読みが戦闘開始 3 秒後まで続き得る。未検証: 先読みが同時にフィオナ待機の描画を遅らせるか(A/B は待機描画と同時に走っているが、frame 間隔への影響は個別に測っていない)。
**テスト側**: 先読みを入れても `ally_motion_p3` の assert・250ms サンプル・timeout は変更しない。

## 2. Aidan 待機(`BattleIdleMotion` の rAF ループ)の遅延蓄積
**前提の訂正**: 以前「連鎖 setTimeout」と述べたのは誤り(`BattleMotion` の `hold:'loop'` はゴブリンレイダー待機のもの)。Aidan の 6コマ待機は `js/battle-idle-motion.js` の `tick()` が `now-r.started>=hold` でコマを進め、`r.started=now` と置く方式。超過分が毎コマ積み上がり、追いつかない。
**測定(`tools/qa/aidan_idle_drift_probe.py`、60 秒、公称周期 1150ms=220,180,220,160,110,260)**:
| 条件 | 平均周期 | 最大周期 | 60 秒の累積ずれ | コマの遅れ 平均 / p95 / 最大 | 「次のコマを飛ばすはずの」遅れ |
|---|---|---|---|---|---|
| Raider・無負荷 | 1203.4 ms (+4.6%) | 1299.9 | +2564 ms | 8.9 / 13.4 / 103.3 ms | 0/300 |
| Raider・CPU競合2本 | 1300.3 ms (+13%) | 1716.6 | +6764 ms | 24.8 / 106.7 / 173.4 ms | 1/278 |
| Raider・競合4本+CPU×4 | 1709.7 ms (+49%) | 2383.2 | +19031 ms | 92.5 / 256.6 / 390.0 ms | 33/211 |
| 通常戦・無負荷 | 1200.0 ms (+4.3%) | 1200.1 | +2448 ms | 8.3 / 13.4 / 13.4 ms | 0/301 |
→ 無負荷でも **常に約 +4.5%**(60Hz の rAF に切り上がるため。コマ毎 約 +8ms)長い。これが現在の「見た目」で、作者が確認した動きはこの速度。負荷が上がるとコマが引き延ばされる(**飛ばしはしない**)。`battle_idle6` は各コマの滞在を rAF で測り ±45ms で比較するので、無負荷では通り、遅れが 45ms を超える負荷下で落ちる(再現済み)。
**時計基準方式の案(いずれも未実装・未承認)**
- K1 `r.started += hold`(持ち越し): 超過分を次のコマへ繰り越す。周期は公称 1150ms に戻る。遅れが 1 コマ分を超えたら `while` で複数コマ進める(=スキップ)。上限(例: 1 回に最大 1 コマ)を設ければスキップを抑えつつ長期ずれを消せる。
- K2 絶対位相 `frame = f((now - t0) mod cycle)`: 状態を持たず常に時計と同期。停止後は現在位相へ即ジャンプ(スキップ)。
**影響の整理**
- 見た目: 公称周期へ戻るため、**待機が現状より約 4.5% 速く見える**(無負荷時)。わずかだが「承認済み演出の速度変更」にあたるので、作者判断が必要。
- フレームスキップ: 現状はスキップなし(引き延ばし)。K1/K2 は負荷下でスキップが出る(上表の最右列が目安: 無負荷 0、強負荷で約 16%)。ジャンプを避けるなら上限付き K1。
- クロスフェード(220ms の `mix`): コマ遷移開始時刻が変わるだけで描画式は不変。スキップ時は from/frame の組を 1 回のフェードにまとめる必要がある。
- 既存モーションとの同期: 待機は他モーションと位相同期していない。pause/resume は `reset()` が `started=now` に戻す(位相を再開地点から)。K2 でも `t0` を `reset()` で更新すれば同じ。フィオナ v3 は既に絶対時計。`hitFrame` イベントは攻撃用の別経路で影響なし。
- テスト: `battle_idle6` の滞在測定は rAF 周期(16.7ms)の量子化が残り、遅い rAF 1 回で前後 2 コマが ±45ms を超えるため、**時計基準化でも負荷下の FAIL は消えない**(無負荷の余裕は増える)。assert は緩めない。
**推奨**: 作者の判断が出るまで変更しない。変更するなら「(a) 速度 +4.5% を許容するか、(b) 公称周期 1150ms でなく現状の見た目に合わせた周期を新たな公称値とするか」「(c) スキップを許すか上限付きにするか」の3点を先に決める。
