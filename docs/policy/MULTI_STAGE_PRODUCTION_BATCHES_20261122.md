# Multi-stage production batches — director approved 2026-11-22
Mandatory for all AI agents, automations and character/world production. Extends Production OS, continuous authoring, blueprint-first and causal retry v3; no asset adoption or future main merge implied.

## Execution units
- Character phase 1: face, hair, body in one native session where supported; phase 2: wardrobe and equipment in one session. Rig/deformation and runtime integration follow applicable gates. Morwen VRoid-first and qualified HairHarpy sequence remain binding.
- Map/environment phase 1: terrain/rock/architecture and physical interfaces, road/bridge/water geometry, placement in asset-local coordinates as appropriate; phase 2: materials/UV, vegetation/props, lighting/composition and scene preview; phase 3: collision/traversal, optimization, integration and regression. Combine adjacent phases when ownership, readiness and budget allow. Village/cliff/meadow/forest and independent modules may run concurrently; never combine conflicting owners into one writer.
- Phase boundaries are checkpoints, not mandatory job boundaries. Prefer one startup/session per meaningful milestone; reuse runtime and verified artifacts. 60–120 minutes is an initial planning heuristic, never a required stop. For verified standard GitHub-hosted public-repository runners, extend productive sessions as needed within the provider's actual job limit (currently plan at most six hours, reserving checkpoint/upload time); verify runner type, billing and effective timeout before dispatch. Avoid per-control/per-object dispatch, fixed idle waits, and report-only stops.

## Execution contract
Before dispatch, verify main policies, existing owner/lease, input hashes, module blueprints, dependency DAG, qualified tools and exact-byte preflight. Record ordered stages with commands/operations, expected outputs, acceptance checks, time budgets, dependencies and checkpoint paths. Never claim an unimplemented GUI operation is executable. Use bounded, tested operations. Within the same session author, preview, measure, correct, save unique editable checkpoints, hash and reopen; record actual evidence. Preserve previous verified inputs. Skip only stages whose exact input/runtime/settings/QA and output hashes are verified. On failure isolate affected dependents, continue independent safe stages; causal retry v3 applies. Stop at time/permission/canon/safety limits with precise resume pointer. Do not promote partial outputs as completed phase. Final matched views and independent G1–G4 remain separate; no automatic adoption/publication/main merge or added cost.
Implementation state: policy approved; individual workflow adapters and actual multi-stage runtime verification required. Existing workflows must be migrated incrementally on their owning PRs, not duplicated or replaced while running.

## Director-approved viewport-first and resumable production (2026-11-22)
- Plan dynamic batches from ready dependency DAG, ownership and measured remaining budget. Record startup count, elapsed time, rework and quality outcomes; reuse verified material/environment caches without weakening provenance. Invalidate affected downstream stages and QA when inputs change; preserve independent successful outputs.
- During native VRoid/Blender editing, inspect actual state against registered blueprint views, landmarks, dimensions, silhouette, topology, contact and material regions; use overlays, wireframe, solid/material preview and inexpensive matched-camera captures as supported. Correct in the same session and measure again. GUI screenshots require a qualified GUI/display; headless Blender uses geometry/projection checks and bounded preview renders, not invented viewport screenshots. Full-resolution matched final renders and independent art/technical QA remain mandatory where applicable. Preview does not certify final lighting, deformation or runtime.
- Save versioned editable checkpoints with SHA, reopen verification, completed stage IDs, input/runtime/settings hashes, dependency invalidation and next operation. Resume from the last verified checkpoint rather than restart or rerender unchanged work.
- A review request is not a job boundary: for a genuinely supported persistent session, checkpoint, publish actual evidence via authenticated channels and accept only authenticated, authorized, schema-validated commands bound to run, owner, checkpoint SHA, revision and one-time request ID. Allow only predefined safe operations; no arbitrary shell/Python, secrets or unapproved changes. Recheck lease and dependency state before applying. Independent ready stages may continue. No assumption that ordinary Actions or chat supports live control.
- For human decisions requiring a pause, prefer a supported environment approval gate between jobs or checkpoint-and-resume with verified state; these do not preserve a running Blender process. A live same-process review bridge is optional only after security, runner lifetime, quota and actual end-to-end qualification. Bound genuine active review waits by remaining job budget, expected response and checkpoint reserve; on verified free standard public runners a longer wait is permitted when retaining state is valuable. Avoid artificial keepalive, public command endpoints, paid services and unnecessary queue occupancy. On timeout or unavailable capability, save/reopen verified checkpoint, release lease safely and resume via authorized existing workflow without repeating completed stages. Never bypass mandatory approval or treat silence as approval.
- Acceptance for each owning adapter: actual in-session edit/measurement/correction, verified checkpoint reopen, selective downstream QA, stale/duplicate/unauthorized command rejection, timeout recovery and no duplicate dispatch. Live pause/resume must be separately demonstrated if claimed. Status: policy approved; adapter and live bridge NOT_RUN. No new asset adoption, cost or merge permission implied.

## Session efficiency and evidence contract — approved 2026-11-22
- Prefer productive persistent sessions, not fixed durations. Schedule checkpoint/upload before the effective deadline, including measured worst-case save/reopen/upload latency and margin; do not rely on cancellation cleanup. On runner loss, restore latest verified off-runner checkpoint. Standard public-repo runner availability and billing must be checked; no larger/paid runner authorization.
- Separate interactive work from expensive rendering: use dirty-module geometry checks and matched low-cost previews; batch cameras and reuse loaded scene/dependency graph where safe. Test persistent render data, adaptive sampling, denoise, instancing and texture reuse against equivalent final quality and memory; no unverified speed claims. Final full-scene review remains required for integration and cross-module changes.
- Publish meaningful checkpoint evidence incrementally with immutable artifact names and manifest (source, native file hash, stage, dependency fingerprint, camera, QA, resume pointer); verify remote availability before declaring durable. No private canon or restricted assets in public artifacts. Use existing authorized transport.
- Decouple independent QA by immutable snapshot: reviewer references exact snapshot hash and scoped correction; writer continues only nonconflicting work. Reject stale feedback unless explicitly rebased and revalidated. Lock only conflicting modules; acquire leases before writes, safely release on verified handoff. No concurrent editing of the same native file.
- Select next ready operation by dependency DAG, quality risk and expected useful progress; preflight changed inputs only with verified baseline. Cache keys include tool/platform/version, input hashes, settings and license; cache hit is not QA. Use deterministic fast checks for measurements, expensive independent visual review at meaningful milestones, full affected regression at integration.
- Record baseline and actual milestone latency, setup time, preview/final render counts, correction cycles, resume success, rework and G1–G4 outcome. Optimize quality-adjusted total effort, not elapsed time alone. Do not create a separate orchestration system if existing Production OS can be extended.
- Live review bridge, long-session adapter and optimizations remain NOT_RUN until tested on existing owners. Policy changes alone do not certify capabilities.

## Deliverable-driven factory targets — director approved 2026-11-22
- Default work order is an actual deliverable candidate, not an isolated operation: one coherent area (terrain, principal buildings, vegetation, paths and scene composition), one complete character candidate, or a batch of distinct NPCs (initial planning target 3–5, not a quota). Large or blocked deliverables may span sessions; report actual completeness and missing modules, never label placeholders or diagnostics as completed assets.
- Main characters: retain mandatory VRoid-first sequence; within native VRoid maximize blueprint fidelity across face, hair, body and wardrobe in substantial continuous sessions. Split where fidelity, native capability, dependency or QA warrants; do not rush export. Qualified HairHarpy for hair gaps before Blender hair sculpting, Blender refinement, rig/deformation and runtime follow existing policy and gates. No premature method switch.
- World: compose existing verified modules in provisional local coordinates where approved, making a coherent editable area candidate before precision refinement; preserve official interfaces and placement uncertainty. NPC: reuse licensed validated bases and modular wardrobe/rig/materials, vary silhouette, face, hair, clothing and occupation with source-grounded designs; check each individual and group diversity, deformation and runtime costs. No canon additions or formal adoption.
- Reuse Production OS rather than invent parallel infrastructure. P0: session controller, blueprint measurement, in-session QA, dependency/lease-aware AI coordination, character and world factory adapters. P1: NPC factory, shared material factory, render optimization and asset library. P1 independent work may proceed when prerequisites ready. Assign by verified capability; no assumed continuous AI thinking, remote agent control or concurrent writers.
- Use up to verified actual free runner limit with save/upload reserve as useful. Plan candidate-level acceptance and next operations before dispatch; continue automatically through ready reversible stages, pause only for real approval or blockers. If AI/runner unavailable, preserve executable checkpoint and precise handoff; no fabricated autonomous activity.
- Validate smallest production-bearing vertical slice in existing owner PRs; evidence must include editable native output, actual matched views, measured blueprint deviations, checkpoint reopen, resume without duplicate stages and scoped QA. Then expand batch size against measured quality and throughput. Candidate completeness is separate from G1–G4 PASS and explicit adoption. Runtime adapters remain NOT_RUN until demonstrated.
