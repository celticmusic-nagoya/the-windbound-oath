# Asset Generation Rules / 画像生成・納品ルール

**Status: MANDATORY（該当タスクのみ）**  
**Scope:** THE WINDBOUND OATH において、画像・アセットの**新規生成または編集を伴うタスク**を行う担当者・AI（ChatGPT、Codex、Claude等）。

## 1. 適用範囲と通常開発の優先規則

- 本規則は、画像・アセットの新規生成、編集、切り出し、スライス、背景透過処理、納品用の画像加工を伴うタスクに**のみ適用**する。
- ソースコード修正、バグ対応、テスト実行、リファクタリング、既存素材を変更しない実装・調査など、**画像制作と無関係な作業には適用しない**。本規則への言及や追加チェックも行わない。
- 画像制作を含まない通常開発の報告では、従来の**箇条書き15行以内のスリム報告制約を最優先**する。
- 通常開発中に画像の新規生成・編集が必要になった場合は、その画像制作部分に限り本規則を適用する。

## 2. 1ファイル＝1独立アセット（原則）

- 原則、**1ファイル＝1つの独立した単体素材**とする。
- 無関係な複数アセット、別バリエーション、独立パーツを1枚に並べた**シート形式・コラージュ形式は禁止**。
- 祭壇の石柱・階段など、単一の完成オブジェクトを構成する装飾は同一素材に含めてよい。別々に使用するエフェクトや状態違いは別ファイルとする。
- 比較シート、素材一覧、ラベル付きコンセプトボードを正式アセットとして納品しない。

### 例外：アニメーション用スプライトシート

- **歩行アニメーション・戦闘モーション等、ゲーム実装上複数コマを1枚に並べる必要があるアニメーション用スプライトシートは例外的に許可する。**
- 生成・依頼時に、**「後続の切り出し・スライス処理を行うためのアニメーション用素材」**であることを明記する。
- 同一アニメーションに属するフレームとして構成し、スライス可能なコマ割り・順序・サイズ・余白・透明背景など、実装側の要件を満たすことを確認する。
- この例外を、無関係なオブジェクトや独立素材を寄せ集めたシートの許可として拡大解釈しない。

## 3. 背景透過・単体切り出し

- ゲーム用の独立素材および背景透過が必要なスプライトシートは原則**透過PNG（有効なアルファチャンネル付き）**で納品する。
- 背景色、背景風景、チェック柄の焼き込み、ラベル、不要な枠・余白、切り抜き残りを含めない。
- 輪郭の欠損、不要な光の縁、半透明の背景残り、オブジェクトの不自然な切断を検査する。
- 背景込みのイラストが明示的に指定された場合はその指示を優先する。ただし、無関係な素材の寄せ集めは禁止する。

### 完全透過の厳格化（単体PNG・エフェクト素材）

- 「完全透過」とは、**素材として意図した形状・光・粒子の外側がアルファ値0（完全透明）**であり、合成時に不要な背景成分が現れない状態を指す。アルファチャンネルが存在するだけでは合格としない。
- アセット周囲、とくに光やエフェクトの周囲に残る**不要な半透明グラデーション、白いもや、スモーク、フレア、広範な低アルファの残留背景**を禁止する。
- 発光そのものに必要な局所的な半透明ピクセルは認めるが、**意図したエフェクト外へ不必要に広がる半透明ピクセルは除去**する。必要な発光表現まで一律に不透明化する趣旨ではない。
- 透明領域のアルファ値が0であることに加え、明暗両方の背景に重ねて境界の汚れ・白縁・黒縁・ゴミ・不自然な四角い領域が現れないことを確認する。
- 透過が不完全な素材は不合格とし、背景除去・修正・再生成の後、再検証する。

## 4. 提出前の非公開セルフチェック（品質ゲート）

画像制作を伴うタスクでは、ユーザーに**提出・表示する前**に内部で以下を確認する。

- [ ] 1ファイル＝1独立アセットか（アニメーション用スプライトシート例外を除く）。
- [ ] 禁止されているシート形式・コラージュ形式になっていないか。
- [ ] 複数コマの場合、明示されたアニメーション用スプライトシート例外に該当し、後続のスライスを前提としているか。
- [ ] 指定された素材・フレーム構成・画風・方向・縮尺・構図に適合するか。
- [ ] 透過が必要な場合、実際にアルファチャンネルが存在し背景が除去されているか。
- [ ] **光・エフェクトの周囲に不要な半透明の背景（もや・フレア等）が残留せず、意図した素材の外側がアルファ0のクリーンな透過状態か。**
- [ ] 明るい背景と暗い背景に合成しても、半透明のゴミ・縁取り・矩形の残留が見えないか。
- [ ] 輪郭、欠損、余白、文字、余計な要素に問題がないか。

**半透明の残留背景が確認された画像は不合格とし、ユーザーに提出・表示せず、完全に背景を除去して再検証する。** **その他の不合格品もユーザーに正式成果物として提出しない。** 内部でプロンプトや編集工程を修正し、可能なら再生成・再検証する。合格品が用意できない場合は、完成と偽らず未完成・理由を報告する。ツールが生成画像を即時表示する場合、非公開検証を保証できないため、その制約を明示し、未検証の出力を正式納品扱いしない。

## 5. 正式採用素材の保護

- 正式採用された素材は無断で加工・差し替え・再生成しない。
- 状態違い、演出、魔法エフェクトは原則独立ファイルで作る（アニメーション用スプライトシート例外を除く）。
- 既存採用素材を変更する場合はユーザーの明示承認を得る。
- 例：`moss_ancient_altar_idle_v1.png` は古代祭壇の正式採用済み通常状態。契約発動エフェクトは別ファイルにする。

## 6. 正式採用素材の保管・台帳管理・納品パス

- **品質チェックおよび実機テスト**（背景透過の見え方、ゲーム画面への合成、位置・縮尺の整合性等）をクリアし、ユーザーが正式採用を承認した画像アセットは、チャット添付や一時フォルダに放置せず、**用途別の所定リポジトリディレクトリへ格納してコミット**する。
- 標準の格納先：
  - 背景・環境・祭壇関連：`assets/images/environments/`
  - 魔法・光・風などのエフェクト関連：`assets/images/effects/`
  - キャラクター・歩行・戦闘スプライト：`assets/images/characters/` 等の専用ディレクトリ
  - UI・ロゴ・アイコン：`assets/images/ui/` 等の専用ディレクトリ
- 既存のランタイムが `img/` 等を参照している場合、**動作中の参照先を無断で移動・削除しない**。所定ディレクトリに原本を保管し、ランタイムへの配置・参照変更は依存関係を確認して別途安全に行う。重複ファイルが生じる場合は台帳に区別して記録する。
- **既存台帳を必ず先に探索する。** `docs/`・`assets/` などにある `ASSET_REGISTER.md`、`ASSET_INVENTORY.md`、素材一覧・README等の既存ファイルを確認し、正式採用素材の記録は既存の正規台帳へ追記・統合する。**別の台帳を新設して記録を分散させることは禁止**。常に単一の最新・正規台帳を維持する。
- 複数の台帳候補が既にある場合は、内容・用途・参照関係を確認し、正規台帳を特定してから更新する。別用途の技術的な素材マニフェストを無断削除せず、正式採用情報の重複管理を避ける。
- **格納・コミット時の台帳自動更新を必須とする。** 品質チェック（単体出力、必要な完全透過など）をPASSした素材を所定ディレクトリへ格納・コミットする作業では、同じ作業内で正規台帳へ最低限以下を記帳する。
  - **アセットID／素材名**
  - **正確なリポジトリ相対ファイルパス**
  - **用途・用途区分**（例：モスの森A3／祭壇契約エフェクト）
  - **透過・品質チェックの合格ステータス**（非透過背景など透過不要な場合はその旨）
- 必要に応じて採用版、実機テスト結果、ランタイム参照パス、コミットSHA、原本ハッシュを追記する。
- 正式採用と同じ納品工程で**ファイルの格納・コミットと台帳更新**を行う。実機テスト待ち等で条件未達の場合は「採用候補／検証待ち」と明示し、正式採用済みとして扱わない。
- **納品・採用報告には、正規の既存台帳に追記・更新した事実と、格納先の正確なリポジトリ相対パスを必ず明記**する。未コミットまたは台帳未更新の場合はその事実を明記し、保存済み・記帳済みと偽らない。
- 採用済み素材の移動・改名・差し替えは、既存参照と台帳を照合し、ユーザーの承認と必要な回帰確認を経て実施する。

## 7. DIRECTIVE / 作業指示書への適用

**画像・アセットの新規生成または編集を含むDIRECTIVE・作業指示書に限り**、冒頭に次の文を明記する。

> **画像制作ルール（必読）：** 画像・アセットの生成・編集に着手する前に `docs/ASSET_GENERATION_RULES.md` を読み、「1ファイル＝1独立アセット（アニメーション用スプライトシートのみ例外）」「不要な半透明もや・フレアを残さない完全透過」「提出前の非公開品質検証」「正式採用後の所定ディレクトリ格納・既存正規台帳への一元化と同時更新・納品パス明記」を厳守する。スプライトシートは後続の切り出し・スライス用であることを明記する。

**画像制作を含まないDIRECTIVEには、この参照文を入れず、本規則に言及しない。** 通常開発では15行以内のスリム報告制約を維持する。

担当AIやセッションが変わっても、該当タスクではこのルールを引き継ぐ。ルール変更にはユーザーの明示承認を要する。
